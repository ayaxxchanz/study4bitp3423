The central exam argument

Adopting a technology is not the same as making it work. Integration connects systems, data, processes and people; implementation needs testing and support; evaluation asks whether the change produced credible value. Financial ROI helps, but is not the only measure of success.

1 · Integrate

Choose APIs, events, data pipelines or cloud/edge deployment according to requirements.

2 · Implement

Manage compatibility, security, ownership and change through suitable rollout.

3 · Evaluate

Use baselines, KPIs, complete costs, ROI and non-financial outcomes.

01Slides 1–7

Meaning of integration

  • Connect new tech with existing systems, data and workflows
  • Include the people, roles and support arrangements
  • Architecture spans users → apps → APIs/events → data → infrastructure
  • Security, monitoring and governance cut across all layers

↳ Install ≠ integrate.

02Slides 8, 12

Strategy 1: APIs

  • Use controlled interfaces between services
  • Specify contracts: formats, auth, permissions, errors, versions
  • Value: reuse, modularity, direct application access
  • Risks: security, limits, downtime and interface changes

↳ API = request controlled service/data.

03Slides 9, 12

Strategy 2: events

  • Publish meaningful events; subscribers respond
  • Example: temperature alert → maintenance ticket
  • Works well when actions need not occur simultaneously
  • Risks: duplicates, ordering, delivery delay, observability

↳ Event = “this happened, react”.

04Slides 10, 13

Strategy 3: data

  • Identify authoritative sources and common meanings
  • Map IDs, formats, quality rules and update frequency
  • ETL/ELT, warehouse and lake are possible approaches
  • Protect lineage, privacy, access, retention and recovery

↳ Moving data ≠ agreeing what it means.

05Slides 11–12

Cloud, edge & hybrid

  • Cloud: centralised scalable processing and analytics
  • Edge: close to devices, less delay/data transfer
  • Hybrid: both, with clear workload placement
  • Choose based on latency, privacy, resilience & support

↳ Place work where requirements are met.

06Slides 13–16

Adoption challenges

  • Technical: compatibility, formats, security, reliability
  • People: skills, resistance, trust, changing procedures
  • Name business and technical owners early
  • Use training, pilot tests, reviews and continuous support

↳ Treat organisational risk as engineering work.

07Slides 16–17, 25–27

Rollout options

  • Pilot: learn within a bounded scope
  • Phased: roll out by site or function; manage dependencies
  • Big-bang: one cutover, higher transition risk
  • Prepare monitoring, recovery, staff support and ownership

↳ Uncertainty high? Start small.

08Slides 18–25

Impact, ROI & next step

  • Set baseline, target and indicators before implementation
  • KPIs: processing time, downtime, errors, adoption and satisfaction
  • ROI % = net benefit ÷ total costs × 100
  • Slide example: (RM180k − RM120k)/RM120k = 50%
  • Consider safety, trust, strategic value before scaling

↳ Impact ≠ installation; ROI ≠ total value.

How to answer a structured question

Check the command word (state, identify, explain, discuss, justify), the number of items requested and the allocated marks. For 4 marks, aim for two distinct explained points; for 6 marks, explain three. For a case study, use the facts in the scenario.
