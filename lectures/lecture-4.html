The central exam argument

A target state describes the future organisational capability, not just a new system. A credible Enterprise Architecture change uses baseline → target → gaps → sequenced roadmap → governance → feedback to turn organisational goals into manageable work.

1 · Define the destination

Describe outcomes and a realistic target across all four EA layers.

2 · Plan the change

Identify gaps, dependencies, stages and accountable owners.

3 · Govern and adapt

Review choices, document exceptions and use iterative TOGAF ADM.

01Slides 1–5, 8

Start with outcomes

  • “Buy a new system” is not a target state
  • State desired student, staff and management results
  • Examples: reliable enrolment status, fewer errors, faster processing
  • Measure current baseline and intended target

↳ Outcome before product.

02Slides 6–9

Baseline vs target

  • Baseline: how the organisation works today
  • Target: agreed realistic future capability
  • Compare the same 4 layers in each view
  • Target includes people, policy, processes & technology

↳ Current ≠ desired.

03Slides 7–9

Target: four layers

  • Business: clear registration workflow and owners
  • Data: agreed definitions + authoritative records
  • Applications: portal and finance/records integrated
  • Technology: secure, monitored, scalable environment

↳ One portal alone is not the target.

04Slides 16–18

Gap analysis

  • Compare baseline ↔ target to reveal missing capabilities
  • Classify: business, data, application, technology, people, governance
  • Record evidence, impact, priority and corrective action
  • Example: inconsistent enrolment status → agree data owner and exchange rules

↳ Gap = missing capability, not just a missing app.

LECTURE 4 · CORE IDEABaseline → Target → Gaps → Roadmap → Governance → Feedback↓ 8 recall branches
05Slides 10–15

Roadmap & dependencies

  • Roadmap sequences initiatives, owners, timing and milestones
  • First: agree data ownership and clean records
  • Next: design and pilot integration
  • Before launch: test security, load, recovery and train support

↳ Order work by dependencies and risk.

06Slides 19–22

Governance

  • Principles, review points, decision rights and owners
  • Review business fit, data, interfaces, security, operations and cost
  • Approve, request revision or document a justified exception
  • Record who accepts residual risk

↳ Governance enables clear decisions.

07Slides 23–25

Simplified TOGAF ADM

  • Vision: outcomes → Architecture: four-layer design
  • Solutions: options → Migration: staged plan
  • Governance: review → Change: update as needed
  • ADM is iterative and adaptable, not mechanical

↳ Vision → Design → Plan → Govern → Learn.

08Slides 17, 25, 28–30

University worked case

  • Target: shared reliable enrolment status
  • Three gaps: no owner, inconsistent data, untested integration
  • Three stages: agree rules → pilot → phased rollout
  • KPIs: processing time, errors, failed transactions, support volume

↳ Write target + gap + action + evidence.

How to answer a structured question

Check the command word (state, identify, explain, discuss, justify), the number of items requested and the allocated marks. For 4 marks, aim for two distinct explained points; for 6 marks, explain three. For a case study, use the facts in the scenario.
